串口调试：printf 背后到底发生了什么

2026-05-30 · 阅读约 5 分钟

每个嵌入式工程师的第一课都是「点亮 LED」，第二课就是 printf("Hello")。 但很多人用了几年 printf，都没意识到它可能是拖垮实时性元凶。

printf 的隐性成本

在 STM32 上最常见的做法是重定向 fputc 到 UART： 

int fputc(int ch, FILE *f) {
  while (!(USART1->SR & USART_SR_TXE));  // 死等发送寄存器空
  USART1->DR = (uint8_t)ch;
  return ch;
}

问题就在那个 while 死等：115200 波特率下， 发一个字节约 87μs，打印一行 50 字符的日志就是 4.3ms。 如果这行日志写在 1ms 控制环里，你的 PID 周期当场翻车。

方案一：DMA + 环形缓冲（推荐）

思路很简单：printf 只负责往缓冲区里拷数据，发送交给 DMA。

  • 日志写入环形缓冲区，临界区保护几微秒，不阻塞任务
  • DMA 搬运完成后中断里启动下一段传输
  • 缓冲区满时丢弃最旧的日志（宁可丢日志，不能堵任务）
void log_write(const char *s) {
  while (*s) {
    ring_buf[head] = *s++;
    head = (head + 1) % RING_SIZE;
  }
  if (!dma_busy) start_next_dma_chunk();
}

方案二：分致日志分级

不是所有日志都值得打印。用宏控制编译期裁剪： 

#define LOG_DEBUG(...)  do { if (g_log_level >= 3) log_write(__VA_ARGS__); } while (0)

量产固件把级别设到 WARN，DEBUG 日志在预处理阶段就被删掉， 零运行时开销。保留现场日志的能力，是量产产品自救的最后手段。

一次产品事故后我们复盘：如果固件里多留一条「重启原因」的日志， 排查时间能从两天缩短到两小时。从那以后每个项目出厂前 都强制检查日志系统。

一个容易忽略的坑

中断里调 printf 是高风险动作——除了阻塞问题， printf 不是线程安全的，ISR 和任务同时打印可能输出交错乱码。 中断里只做一件事：把消息塞进队列，让低优先级任务去打印。

日志系统是嵌入式工程里典型的「平时没人看，出事救你命」的基建， 值得在每个项目开工第一天就搭好。
